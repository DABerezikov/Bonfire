## Уточнение владельца и результат

Владелец потребовал один источник фаз и отсутствие жёсткой связи с поставщиком.
Поэтому прежнее предложение оставить два вычисления заменено общей абстракцией
`MoonCalendar/ILunarPhaseCalculator`. Сам MoonCalendar не ссылается на пакет
Astronomy Engine и не создаёт поставщика. `MoonPhase` принимает калькулятор
конструктором; MoonAge — свойство экземпляра, статического источника больше нет.
Названия восьми фаз преобразуются общей чистой функцией LunarPhaseNames.

Единственная производственная реализация — AstronomyLunarPhaseCalculator
в Bonfire/Infrastructure, пакет CosineKitty.AstronomyEngine 2.1.19 подключён
только к внешнему WPF-проекту. Реализация выбирается только в ServiceRegister.
MoonPhaseCalendar и LunarTrendCalendar зависят от интерфейса калькулятора;
сервис рассады и ViewModel используют существующий ILunarCalendar.
Подмена одного калькулятора в DI проверена для обоих потребителей.

Средний возраст по эпохе удалён из вычисления фаз. Возраст теперь означает
прошедшие сутки с последнего астрономического новолуния, а восемь названий
вычисляются по углу Луна–Солнце. DateTime учитывает время и Kind;
Unspecified в прежнем API трактуется как местное время компьютера.
Планирование отдельно использует DateOnly и полдень часового пояса региона.
Сохранённые исторические строки фаз не пересчитываются миграцией.
Приближённые расстояние/широта/долгота/зодиак не используются как источник фаз
и в этом шаге не меняются.

LunarSowingPolicy / SowingRecommendations дают Available, Conflict или Unavailable.
Внутри возможного окна первыми идут дни устойчивого окна; если подходят
только остальные дни, возвращается предупреждение. При конфликте показываются
ближайшие более ранний/поздний дни в явно переданном пределе поиска, сдвиг
от ближайшей границы и прогнозы. Для рассады есть возраст на исходную высадку,
для прямого посева — всходы и зрелость без фиктивного возраста.
Ручной выбор оценивается и не перезаписывается.

RecommendSowing возвращает агрономический preview даже при недоступности фаз,
кэширует дни только в пределах одного запроса и поддерживает отмену.
Календарный адаптер пока допускает 1700–2100 годы — диапазон доступной
эталонной службы USNO. За его пределами доступен агрономический расчёт.
Независимые контрольные события покрывают январь, февраль и июль 2027;
исчерпывающей проверки каждого дня 1700–2100 не проводилось.

Источники: [USNO, события 2027](https://aa.usno.navy.mil/calculated/moon/phases?year=2027),
[определение фаз и диапазон службы](https://aa.usno.navy.mil/data/MoonPhases),
[C# API Astronomy Engine](https://github.com/cosinekitty/astronomy/tree/master/source/csharp),
[зафиксированный пакет](https://www.nuget.org/packages/CosineKitty.AstronomyEngine/2.1.19).
Численный допуск контрольных моментов — ±10 минут, не обещание точности
для всех дат. Дневная классификация не добавляет запрет переходного дня.

## Цель и файлы

Подбирать посев только по Growing/Waning. Запреты дней новолуния/полнолуния,
дополнительные сутки исключений и зодиак не входят в требования.
Новые: `Bonfire.Application/Planning/ILunarTrendCalendar.cs`,
`Bonfire.Domain/Planning/LunarSowingPolicy.cs`, `SowingRecommendations.cs`,
адаптер в `Bonfire/Infrastructure/`, профильные тесты Models.Tests/Services.Tests.
Контракт ILunarCalendar.GetPhase и сохранённые строки фаз сохраняются.
Источник пересчёта MoonPhase заменён по прямому уточнению владельца выше.

## Контракт и дневная классификация

Порт возвращает Result<LunarTrend> для даты и зоны региона, а не строку UI
или готовое решение «благоприятно». В Domain LunarTrend — Growing/Waning;
отсутствие данных выражено ошибкой порта и диагностикой preview, не новой фазой.
Проектная конвенция: классификация на местное полуденное время. День перехода
получает одну из двух фаз на этот момент и не запрещается целиком.
У выбранного источника проверить определение фазы, точность и работу с UTC/зоной.
Текущие широкие строки «Новолуние»/«Полнолуние» нельзя объявлять запретом.
Сначала проверить достаточность существующего расчёта возраста Луны по эталону;
новая библиотека нужна только при доказанной недостаточности, без обязательного
сетевого запроса на каждый расчёт. Выбор поставщика документируется после проверки.

## Правила и псевдокод

- AboveGround предпочитает Growing, RootCrop — Waning.
- Никаких лунных ограничений высадки, пикировки и сборов.
- Неизвестная лунная группа — рекомендация недоступна, агрономический расчёт остаётся.
- Ручную дату можно сохранить с объяснением несовпадения предпочтению.

```text
ClassifyDay(day, regionZone):
    localMoment = day.AtLocalNoon(regionZone)
    return calendar.GetTrend(localMoment.ToUtc())

Recommend(schedule, group, trends, limitDays):
    inside = Days(schedule.PossibleSowingWindow)
        .Where(day => Matches(group, trends[day]))
        .Map(day => EvaluateCandidateForMethod(day, schedule))
    if inside.Any:
        return Available(Rank(inside, resilientWindowFirst=true))
    return Conflict(original=schedule.Windows,
        earlier=NearestMatchingBefore(window.Start, limitDays),
        later=NearestMatchingAfter(window.End, limitDays))
```

При расхождении только с устойчивым окном — предупреждение, при отсутствии
дней во всём возможном окне — конфликт. Предлагаемый предел поиска 35 дней
в каждую сторону сохраняется как явно переданное проектное значение.
Отсутствие данных и исчерпание поиска имеют разные причины.
Сдвиг объясняется от ближайшей границы исходного окна. Для рассады показать
возраст на исходную высадку и готовность; для прямого посева — изменение всходов
и зрелости. Исходные даты и ручной выбор не заменяются автоматически.

## Последовательность и проверки

1. Red/Green: обе группы, обе фазы, ручной выбор, отсутствующая группа.
2. Контрольные даты USNO по разные стороны новолуния/полнолуния, включая смену
   местной даты Томска. Проверить точный смысл дневной классификации.
3. День новолуния/полнолуния не исключён, первая/последняя четверти не запрещены.
4. Нет подходящих дней: обе альтернативы, предел поиска, отказ поставщика.
5. Прямой посев и рассада дают правильные, разные объяснения сдвига.
6. MoonCalendarBehaviorTests проверяют фазы по USNO; прежние приближённые
   численные ожидания фаз заменены по указанию владельца об одном источнике.
   Контроль остальных старых функций сохранён. Новый порт проверяется по
   независимому эталону, а не сравнением с самим собой.

Гейт: профильные Models.Tests/Services.Tests. Готовность: только Growing/Waning,
объяснимые рекомендации, нет скрытых запретов и изменения исторических фаз.
