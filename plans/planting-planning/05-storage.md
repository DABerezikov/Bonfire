# Этап 5. Хранение сезонных планов и независимых снимков

Статус: план. Зависимости: этапы [1](01-contracts.md)–[4](04-lunar.md).
[Общий план](README.md).

## Цель и файлы

Сохранять партии, исходные параметры, результаты и ручной выбор так, чтобы план
открывался после перезапуска и не менялся при редактировании справочника.

Новые: `BonfireDB/Entities/Planning/SeasonalPlantingPlan.cs`, `PlannedBatch.cs`,
`BonfireDB/Planning/DbPlantingPlanReader.cs`, `DbPlantingPlanWriter.cs`,
`PlanningSnapshotDbMapper.cs`, `Bonfire.Application/Planning/PlanningStoragePorts.cs`.
Изменить: `BonfireDB/Context/DbBonfire.cs`, `RepositoryRegister.cs`, миграции и snapshot.
Тесты: `Tests/Services.Tests/PlantingPlanStorageTests.cs`,
`PlantingPlanMigrationTests.cs`; при необходимости `Tests/Repository.Tests/`.

## Предлагаемая схема

| Объект | Содержимое |
|---|---|
| SeasonalPlantingPlan | ID, название, год сезона, RegionId, версия записи |
| PlannedBatch | ID, PlanId, порядковый номер, CultureId/SortId, условия, целевые растения, режим количества, версия записи |
| Входной снимок партии | Ручное окно высадки, значения и источники G/A/P/H, проценты, лунная группа, зона, overrides |
| Результат расчёта | Возможное/устойчивое окна, число семян, версия алгоритма, версия лунных правил, момент расчёта |
| Выбор пользователя | Выбранные точные даты операций, ручное/рекомендованное происхождение, ручное количество |

Техническое представление снимка (колонки/owned types/версионированный JSON)
выбрать до миграции по возможностям EF/SQLite проекта. Основные фильтры
PlanId, CultureId, SortId, условия, выбранная дата посева должны быть индексируемы;
не прятать все данные в непрозрачную строку. Если используется JSON, обязательны
SchemaVersion, проверка чтения и миграция формата, а не catch с пустым профилем.

План не требует SeedId: сорт может планироваться до покупки пакета. При необязательной
ссылке на пакет его удаление не должно удалять план. Привязка к грядкам не вводится
на этом этапе. Имена культуры/сорта/региона и часовой пояс сохраняются в снимке,
чтобы исторический план можно было объяснить после изменения справочников.

Конкретные FK и политика удаления выбираются после аудита существующих Delete
культуры/сорта: не ухудшать старое поведение неявным Restrict и не допускать
Cascade планов из библиотек. Предпочтение для необязательных справочных ссылок —
SetNull с сохранённым снимком, для новых каталогов — архивирование.
Домен нового редактирования по-прежнему требует проверенные положительные ID;
исторический read DTO может содержать Option<ID> и сохранённое имя.

## Запись и конкуренция

Загрузка плана возвращает immutable DTO; запись принимает проверенный агрегат,
не EF-граф из UI. На каждом изменении перечитать свежую запись.
Версия — управляемый приложением concurrency token: SQLite не предоставляет
автоматический SQL Server rowversion. При несовпадении вернуть конфликт,
не перетирать позднее изменение другого редактора.

```text
SaveBatch(validatedEdit, expectedVersion):
    entity = LoadFreshBatchAndPlan(validatedEdit.Id)
    if entity.Version != expectedVersion:
        return Failure("План изменён; обновите данные перед сохранением")
    ValidateReferencesAndIdentity(validatedEdit, entity)
    ApplyOnlyEditableFields(entity, validatedEdit)
    entity.Version += 1
    await SaveChangesAsync()             // одна атомарная операция
    return Success(MapIndependentReceipt(entity))

ReadPlan(id):
    return QueryNoTracking(id).ProjectToImmutableDto()

DeleteBatch(id, expectedVersion):
    entity = LoadFresh(id)
    CheckVersion(entity, expectedVersion)
    RemoveOnlyPlannedBatch(entity)
    await SaveChangesAsync()
```

Пересчёт/сохранение партии не пишет SeedsInfo, SeedlingInfo, GardenPlan или ячейки.

Дополнение: PlannedBatch хранит дискриминатор способа и соответствующее исходное
окно: TransplantingWindow либо DirectSowingWindow. Маппер проверяет допустимое
сочетание; неприменимые поля не сериализуются как возраст/дата 0. Снимок прогноза
хранит вегетацию от всходов, либо причину отсутствия прогноза. Ссылки на
фактические партии/сборы не добавляются. Снимки площади и урожайности — по этапу 9
с явными базами норм в кг. Проверить round-trip обоих способов и неверный дискриминатор.
Удаление сезонного плана удаляет только его плановые партии. Для составной записи
всего плана один SaveChanges; частичного сохранения партий при отказе быть не должно.

## Последовательность и проверки

1. Аудит текущей схемы/каскадов и возможностей mapping для DateOnly/decimal/owned.
2. Red/Green: SQLite round-trip полного плана, двух партий и всех None/ручных полей.
3. Добавить миграцию и индексы; проверить свежую и обновлённую БД отдельно.
4. Red/Green: конфликт версии, отказ SaveChanges, отсутствие частичной записи.
5. Проверить удаление плана и библиотеки без потери фактов; архивные ссылки читаются.
6. Изменить справочник и перезапустить чтение: сохранённый снимок остаётся прежним.
7. Применить миграции повторно: данные не дублируются; старая рабочая БД не используется.

Гейт: профильные Services.Tests с временной реальной SQLite. InMemory не считается
доказательством FK, concurrency или миграций. Готовность: подтверждённая схема,
полный round-trip и атомарность, нет изменения исторических остатков и посадок.
