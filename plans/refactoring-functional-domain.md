# Актуальный план: богатая модель и функциональное ядро

Статус: выполняется; первые результаты описаны в [журнале реализации](refactoring-progress.md).
Дата: 24.10.2026. База: `8a51f5f`.
Дополняет и уточняет [исходный архитектурный план](refactoring-baseline.md).

## Цель и принципы

Получить богатую доменную модель с функциональным ядром. Правила выражаются типами
и чистыми преобразованиями; WPF, EF и файловые операции выполняют внешние эффекты.

- Модели отвечают за посев, списание, прорастание, пересадку, гибель и инварианты.
  Application загружает данные, вызывает операции и сохраняет результат.
- Проверенные value objects представляют количество, вес, диапазоны и схему посадки.
  Публичный API не позволяет обходить инварианты.
- Доменные модели иммутабельны. Операции возвращают новое состояние; `With…`
  применяется там, где подходит предметной области. EF/WPF-модели остаются на границах.
- Обязательные значения всегда существуют; отсутствие выражается `Option<T>`,
  ожидаемые отказы — `Result<T>`. Перед добавлением типов проверить имеющиеся
  реализации и расширить общий механизм без параллельного toolkit.
- Композиция функций и результатов, pattern matching и явные варианты состояний
  описывают правила декларативно. Абстракции должны упрощать понимание сценария.
- Для закрытых sealed-иерархий полиморфный `Map` — extension в отдельном статическом
  классе с исчерпывающим pattern matching, согласно `AGENTS.md`.

## Контракт отсутствующих значений

В Domain и Application исключить неявное отсутствие, возвраты `null` и подавление
nullable через `!`. На входе из WPF, EF и внешних API nullable преобразуется в явный
результат. Различать «не указано», «не применимо», ноль и пустую строку по смыслу
конкретного поля; не подставлять значения молча.

Некорректные старые записи должны давать диагностируемый результат. Их исправление
или миграция требуют отдельного решения, а не угадывания при маппинге.

Затрагивается: `Bonfire/Models`, `Bonfire/Services`, `BonfireDB/Entities`, документация.

- Проследить поля и операции от UI до БД; описать агрегаты, владельцев, связи,

- Зафиксировать сохраняемое поведение отдельно от исправлений, соглашения
  `Option`/`Result` и направления зависимостей из исходного плана.
- Готовность: проверенная карта без смысловых дублей; неоднозначности явно отмечены.

### 2. Первый полный сценарий: посев и независимый черновик

Затрагивается: `SeedlingsViewModel`, `SeedsService`, `SeedlingsService`,
`SeedlingMapper`, UnitOfWork, новые Domain/Application-типы и соответствующие тесты.

- Сначала Red-тесты атомарности, отказа сохранения и изоляции черновика.
- Ввести необходимые типы количества и источника. Чистая операция рассчитывает
  новые остатки и партию; Application сохраняет оба изменения одним UnitOfWork.
- Ошибки и отсутствие источника возвращать явно. UI обновлять после успеха.
- Готовность: отказ не оставляет частичного сохранения; отмена не меняет оригинал;
  сценарий служит проверенным образцом для следующих модулей.

### 3. Запуск и внешние эффекты

Затрагивается: `App`, `Program`, `DbRegistrator`, `DbInitializer`, DI-регистраторы,
команды и обработчики ошибок.

- Изолировать время, диалоги и системные действия узкими интерфейсами там,

- Готовность: строгая проверка DI, запуск с временной БД, предсказуемое завершение
  и обработка ошибок; рабочая БД не используется тестами.

### 4. Семена и библиотеки

Затрагивается: `SeedsViewModel`, `LibraryEditorViewModel`, сервисы, модели и мапперы.

- Перенести создание и изменение в проверенные операции богатых моделей.

### 5. Рассада — выполнено для существующих сценариев

- Готовность: доменные операции тестируются без БД/моков; отмена сохраняет исходную
  модель; правила количества и единиц проверены на границах.

## Общие критерии и доказательства

- Domain не зависит от WPF, EF, DI и файловой системы; Application не зависит от
  конкретных реализаций хранения и UI.
- Доменная операция проверяется без моков и БД; публичный API защищает инварианты.
- Отсутствие и ожидаемые отказы обрабатываются исчерпывающе.
- Для количеств проверяются законы сохранения, границы и согласованность единиц.
- Все пять тестовых проектов проходят: `dotnet test Bonfire.sln`. Сохраняется
  защита поведения существующими 633 проверками; тесты адаптируются к новым границам
  без потери проверяемых сценариев.
- Исправления и новые правила: Red → Green → Refactor. Чистый перенос поведения
  обрамляется характеристическими проверками до и после изменений.
- Хранение проверяется на SQLite, включая отказ и откат; миграции сопровождаются
  доказательствами сохранности данных. Полный startup, нативные диалоги и DPI
  остаются отдельным процессным/визуальным гейтом.
- Каждый этап — работающий результат и отдельные сфокусированные коммиты.
  Merge в `master` — только по явному запросу владельца.
