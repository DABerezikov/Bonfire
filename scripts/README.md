# Развёртывание Bonfire

Запускайте из корня репозитория в Windows PowerShell 5.1 или PowerShell 7.
Для сборки нужен .NET SDK из `global.json`, для записи — доступ к сетевой папке.
Закройте Bonfire на всех компьютерах, использующих эту установку.

```powershell
# Предварительный просмотр без сборки и записи
.\scripts\Deploy-Bonfire.ps1 -WhatIf

# Release, win-x64, self-contained; затем установка в \\MONOBLOCK\Bonfire
.\scripts\Deploy-Bonfire.ps1

# Установка из заранее подготовленного dotnet publish
.\scripts\Deploy-Bonfire.ps1 -PublishDirectory .\artifacts\my-publish
```

CI и скрипт используют общий профиль `FolderProfile`: Release, win-x64,
self-contained, единый `Bonfire.exe` с библиотеками .NET, WPF и SQLite.
Устанавливать .NET на целевом компьютере не требуется. Нативные библиотеки
распаковываются средой .NET при запуске; настройки остаются внешними файлами.

Скрипт сначала публикует приложение в уникальный локальный каталог
`artifacts/deploy-publish/`, затем сохраняет прежние файлы в
`\\MONOBLOCK\Bonfire\backups\yyyyMMdd-HHmmss-fff-<id>\`.
В бэкап входят БД, настройки и отчёты; прежние бэкапы не копируются повторно.
Каждый файл проверяется по SHA-256. Маркер `.backup-complete` означает, что копия
завершена; без него каталог считается незавершённым. Только после этого
старые бинарники приложения убираются из установки, затем записывается новая
публикация. Прежняя версия остаётся только в бэкапе, включая DLL и локализации,
которые больше не нужны единому EXE. Пустые каталоги этих локализаций удаляются.
Перенос выполняется как проверенная копия и удаление оригинала после завершения
бэкапа; при ошибке установки старые бинарники возвращаются на место.
Скрипты runner, его архивы и произвольные пользовательские файлы сохраняются.

Файлы `*.db`, `*.db3`, `*.sqlite`, `*.sqlite3` и их `-wal`, `-shm`, `-journal`
не устанавливаются из публикации и не изменяются. На время копирования они
открываются с запретом записи. Существующие `appsettings*.json`, `*.config`,
каталоги `Reports`, `Logs`, `backups` сохраняются. При первой установке настройки
копируются, БД из публикации — никогда. Приложение скрипт не запускает;
штатные миграции при последующем запуске приложения остаются прежними.

При ошибке замены скрипт пытается восстановить уже затронутые файлы из бэкапа.
При потере сети или питания автоматическое восстановление не гарантируется:
закройте приложение и восстановите файлы из последней завершённой копии.
БД при откате версии вручную не заменяйте.
После успешной установки скрипт оставляет три последние завершённые резервные
копии в `backups`; текущая установленная версия хранится отдельно. Текущая копия
перед обновлением всегда сохраняется, даже если часы были переведены назад;
остальные выбираются по дате в имени каталога. Старые копии удаляются целиком,
включая их снимки БД и отчётов. Рабочие БД, настройки и отчёты не затрагиваются.
Очистка выполняется под общей блокировкой обновления. При `-WhatIf` и отказе
установки копии не удаляются. Незавершённые копии без `.backup-complete`, каталоги
с посторонними именами и ссылки не очищаются. Перед рекурсивным удалением
проверяются границы `backups`, отсутствие вложенных ссылок и доступность файлов.
При невозможности очистки выдаётся предупреждение; обновление остаётся успешным,
а число копий может временно превышать три. Следующее обновление повторит очистку.
При аварийном завершении может остаться `.bonfire-deploy.lock`; удаляйте его
только убедившись, что другое развёртывание не выполняется.

Проверки на изолированных локальных файлах, без обращения к MONOBLOCK:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Tests/Deployment/Deploy.Tests.ps1
dotnet test Bonfire.sln
```

Для непрерывного развёртывания используйте Windows runner с доступом к ресурсу:
тесты → публикация → этот скрипт. Запуски необходимо сериализовать; приложение
должно быть закрыто. Облачный runner сам по себе не имеет доступа к локальной
сети. Учётную запись runner настройте с правами на ресурс, без паролей в скрипте.

Проверено: 9 сценариев скрипта, общий гейт 1538/1538, реальная self-contained
Release-публикация и установка 459 файлов в изолированную локальную папку.
Развёртывание на MONOBLOCK и работа через SMB пока не проверялись.

Установка GitHub runner с запуском при входе пользователя на MONOBLOCK:
[Install-BonfireRunner.md](Install-BonfireRunner.md).

Workflow `Bonfire — MONOBLOCK` запускается при push в `master` или вручную через
GitHub Actions. Сборка, полный тест-гейт и публикация выполняются на GitHub.
На MONOBLOCK `Update-BonfireInteractive.ps1` проверяет процесс именно этой установки.
Если Bonfire закрыт, обновление выполняется без окна. Если открыт — показывает
XAML-подтверждение на 5 минут; согласие разрешает штатно закрыть приложение.
Отказ/тайм-аут отменяют установку. Запуск Bonfire во время подготовки запрещает
запись без нового согласия. После успеха `.bonfire-version.json` содержит
commit и путь резервной копии. Автоматического запуска новой версии нет.


Выгрузка артефактов закреплена SHA upload-artifact v6.0.0 (Node.js 24).
Ручное получение архива доступно через `Get-BonfireArtifact.ps1` и системный
`curl.exe`; для GitHub API нужен токен с actions:read. В текущем workflow этот путь не запускается. GH_TOKEN передаётся шагу
через окружение и используется только для api.github.com. Подписанная ссылка
обновляется перед каждой попыткой и передаётся curl через stdin без bearer.

Три попытки по 900 секунд (15 минут): подключение не дольше 15 секунд, скорость ниже 16 КиБ/с
за 30 секунд прерывает передачу. При сетевом отказе .part продолжается; при отказе
Range (включая HTTP 416) начинается заново. HTTP-ошибка/истёкшая ссылка сохраняет
байты. Неверный SHA сбрасывает .part. Ключ кеша включает id артефакта и digest.
Кеш в RUNNER_TEMP сохраняется между попытками, но не обещает сохранность между job.

Перед распаковкой обязательны size и SHA-256 из API текущего run/name. Распаковка
идёт в новую staging-папку рядом с выходом; только после успеха папка переносится
в artifacts/publish. Непустой выход запрещён. Отказ даёт exit 1 и не запускает
установку. Прежний облачный путь имел лимиты шага 48 минут и deploy 60 минут; он заменён локальной командой git publish.
Скрипт не исправляет плохой маршрут до Azure: при устойчиво плохой связи он
завершается с понятным отказом, сохраняя исходную установку.

Проверки: ArtifactDownload.Tests.ps1 (13 сценариев), включая настоящий локальный
TCP-сервер/curl, обрыв, Range, HTTP 416, timeout, неверный SHA, ZIP и кеш.
[План и псевдокод](../plans/resumable-artifact-download.md).
Механизм тайм-аутов и продолжения: [руководство curl](https://curl.se/docs/manpage.html).


Ручное обновление с другого компьютера поддерживает штатный ресурс
`\\MONOBLOCK\Bonfire` непосредственно как каталог приложения. Исключение
проверки корня разрешено только этому точному ресурсу без учёта регистра;
корни дисков и иных сетевых ресурсов по-прежнему запрещены. Проверки WhatIf
подменяют только наличие сетевого каталога, не обращаются к сети и не пишут туда.
Гейт скрипта: 19 сценариев, включая сохранность данных, блокировки, откат и retention.


Проверка SHA-256 исходника читает поток с FileShare.ReadWrite: открытый в Excel
документ, разрешающий чтение, можно скопировать и проверить без закрытия редактора.
Контрольная сумма копии по-прежнему обязана совпасть; при отказе чтения или
несовпадении обновление не начинается. БД отдельно защищены от записи, бинарники
установки проверяются на исключительный доступ. Гейт: 20 сценариев PowerShell 5.1.


stdin-конфигурация curl передаётся в UTF-8 без BOM независимо от кодировки консоли.
В PowerShell 5.1 кодировка задаётся на время Process.Start и сразу восстанавливается
в finally; глобальная настройка консоли между вызовами не изменяется.
Регрессия включает UTF-8 с BOM, как на hosted runner, и кириллицу в пути partial.


При наблюдаемой скорости около 7 МБ за 120 секунд архив 93 МБ требует примерно
27 минут. Бюджет трёх попыток — 45 минут плюс запас шага на API, хеш и распаковку;
после скачивания остаётся 12 минут на подтверждение и установку. Сохранены прежние
пределы подключения (15 секунд) и низкой скорости (16 КиБ/с за 30 секунд).


## Локальная публикация после push

В D:\Dmitry настроен локальный alias репозитория:

```powershell
git publish
```

Команда разрешена на master с чистыми отслеживаемыми файлами и origin Bonfire
(проверяются fetch и push URL). Неотслеживаемые данные не попадают в сборку.
После успешного push конкретного SHA создаётся архив этого коммита в отдельной
папке TEMP\Bonfire-local-publish. Полный Release-гейт, скриптовые проверки и startup/exit
smoke выполняются на снимке, затем FolderProfile и проверка единого exe. Изменение
рабочей папки после push не влияет на сборку. Перед установкой remote проверяется
повторно; более новый origin/master запрещает установку старой версии.

Установка использует Update-BonfireInteractive.ps1: бэкап, SHA-256, сохранение БД и
настроек, блокировка занятых файлов, запись версии. Bonfire на других компьютерах
должен быть закрыт; удалённые процессы по SMB команда не закрывает. Если уже установлен
этот SHA, сборка и повторный бэкап пропускаются. Параллельные git publish блокируются
общим файлом .git/bonfire-publish.lock; после выхода дескриптор освобождается.

Если push прошёл, а проверка/установка отказала, push не откатывается. Снимок остаётся
для диагностики, команда завершает работу кодом 1. После устранения причины повторите
git publish. После успешной установки удаляется только собственный временный снимок.
Обычный git push отправляет код без локальной установки. GitHub оставляет проверки,
публикацию архива и TRX; облачная установка на self-hosted runner отключена.

Для другого клона настройте alias из его корня:

```powershell
git config --local alias.publish '!powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File scripts/Publish-Bonfire.ps1'
```

Для изолированной проверки можно передать -Destination с тестовой папкой; обычная
команда использует \\MONOBLOCK\Bonfire. [План и псевдокод](../plans/local-publish-after-push.md).

На время git publish Windows PowerShell получает штатный PSModulePath без
унаследованных путей PowerShell 7; после завершения прежнее окружение возвращается.
Это обеспечивает доступность Get-FileHash и архивных команд при запуске через Git.
