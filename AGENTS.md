## Структура и архитектура

Bonfire — WPF-приложение для учёта семян, рассады и планирования огорода на .NET 10.

- `Bonfire/`: `Views/` — XAML, `ViewModels/` — представление, `Services/` — бизнес-логика, `Models/` — DTO; `Views/Image/`, `Templates/`, `Resources/` — изображения и оформление.
- `BonfireDB/`: `Context/`, `Entities/`, `Migrations/`; репозитории и UnitOfWork находятся в корне проекта.
- `Bonfire.Domain/`: независимое функциональное ядро; `Functional/` — общий `Result`, `Seeds/` — количество, остаток и чистая операция посева. Не добавляйте зависимости на WPF/EF/DI.
- `Bonfire.Application/`: операции приложения и порты хранения/календаря; зависит только от Domain и runtime. `Seedlings/` содержит сценарий посева без EF/WPF-моделей.
- `MoonCalendar/`: расчёты лунного календаря.
- `Tests/`: пять проектов xUnit.

Соблюдайте цепочку View → ViewModel → Service → Repository → DbContext → SQLite. Используйте базовый ViewModel, `LambdaCommand`/`LambdaCommandAsync` и существующие DI-регистраторы. Сервисы предоставляйте через интерфейсы и регистрируйте в `ServiceRegister`; репозитории — в `RepositoryRegister`.

Для перенесённого посева сервис делегирует Application, который вызывает Domain и порты; `BonfireDB/Sowing/` реализует порт сохранения. Не возвращайте EF-сущности в контракты Application. Отсутствие в новых контрактах выражайте через `Option`, преобразуя nullable только на внешних границах.

Для nullable ↔ Option используйте общие extension-методы `ToOption()`/`ToNullable()` из `Bonfire.Domain/Functional/OptionExtensions.cs`. Не дублируйте эти преобразования локальными методами или одинаковыми тернарными выражениями. Пустая строка, пробелы и ноль сохраняются как Some; только null означает None.

Редактирование культуры проходит через `Application/Libraries/UpdateCulture` и `Domain/Libraries/CultureDefinition`; сохранение — через `BonfireDB/Libraries/DbCultureWriter`. Имя и класс обязательны, идентификатор — `CultureId`. Непустой текст и пользовательские классы сохраняются без неявной нормализации.

Редактирование производителя использует `ProducerDefinition`, `ProducerId`, `UpdateProducer` и `DbProducerWriter`. Общий value object `LibraryName` проверяет названия культуры и производителя; не дублируйте эту проверку в новых доменных моделях. Application возвращает DTO, EF-типы остаются на границе совместимости `LibraryService`.

Библиотечное редактирование сорта использует `SortLibraryEdit`, `SortId`, `UpdateSort` и `DbSortWriter`. Меняются только название (с Trim) и культура всех связанных растений. `CultureChange = None` сохраняет существующие связи; культура принадлежит Plant, а не PlantSort. Результат `UpdateSortAsync` — DTO со связями растение → культура для синхронизации UI; характеристики сорта здесь не сохраняйте.

Редактирование пакета и характеристик проходит через `SeedEditMapper → Application/Seeds/EditSeed → Domain/Seeds/SeedEdit → BonfireDB/SeedEditing/DbSeedEditWriter`. Порт принимает только проверенную модель; пакет, общий сорт, производитель и варианты цвета/созревания сохраняются одним SaveChanges. `SeedPackage` и `SortCharacteristics` иммутабельны; `*Values` — входные значения, проверяемые фабриками. Nullable преобразуйте в Option на границе и обратно только при записи EF. В этом сценарии текст сорта не обрезается, CultureId не меняется. `SaveSeedEditAsync` возвращает Result: при отказе UI сохраняет черновик.

`SeedsViewModel.EditedItem` — `SeedEditorDraft`, а не Seed. Пакет редактируется через `SeedPackageEditModel` поверх иммутабельного `SeedPackageValues`; характеристики — через существующий `SortEditModel`. Маппер читает EF только при открытии записи; сервис сохранения принимает `EditSeedFromViewModel`. Dirty пакета и производителя сравнивается с исходным снимком, не с живым кэшем. Отсутствие черновика допускается только на WPF-границе при снятом выборе; команда проверяет его явно. Новые EF-графы для редактирования не создавайте.

Добавление/пополнение проходит через `SeedAcquisitionMapper → AcquireSeeds → SeedAcquisition → DbSeedAcquisitionWriter`. Не передавайте кэш EF из UI для принятия решения: порт читает свежие данные. Количества рассчитывает Domain, локальную дату покупки задаёт TimeProvider. Варианты результата — Created/Replenished внутри Result. Совпадение пакета — точные культура/сорт/производитель и год годности; смена производителя общего сорта сохраняет прежнюю семантику. Отсутствующий остаток в граммах возвращает отказ, не подставляйте ноль. Общий маппинг SeedsInfo ↔ SeedPackageValues находится в SeedPackageDbMapper.

Удаление с причиной проходит через `SeedDeletion → DeleteSeed → DbSeedDeletionWriter`. Причина обрезается по краям, пустая строка допустима; null от диалога означает отмену до обращения к сервису. Один SaveChanges сохраняет DisposeComment и удаляет только Seed; SeedsInfo, общий Plant и рассада остаются. Результат — DTO с ID внутри Result, кэш и черновик UI меняются только после успеха. Подсказки семян перестраивайте общим RebuildSeedSuggestions.

Чистый возврат количества реализован в `SeedStock.WithReturned`, возврат в пакет — в `SeedPackage.WithReturned`. Оба возвращают новый экземпляр внутри Result; единицы и переполнение проверяются существующим SeedAmount. Нулевой возврат сохраняет отсутствующий вес как None; положительный возврат граммов при неизвестном остатке даёт отказ.

Рассада самостоятельна после посева; SeedId — информационная ссылка, исходный пакет разрешено удалить. Удаление рассады проходит через XAML-диалог `DeleteSeedlingDialog`, явный `SeedlingRemoval` и `Application/Seedlings/DeleteSeedling`. Discard удаляет без обращения к семенам; CorrectSowing возвращает исходные Quantity/Weight через чистый ReturnTo. `DbSeedlingDeletionWriter` читает свежую партию и сохраняет возврат/удаление одним SaveChanges. Отсутствующий пакет запрещает только возврат; UI сохраняет выбор/черновик и показывает причину. Option.None от диалога — отмена; DTO результата обновляет остатки и подсказки только после успеха. Исторические SeedlingInfo и связанные места посадки сохраняются согласно текущим необязательным связям; схему и каскады попутно не меняйте.

Всходы проходят через `SeedlingBatch → ChangeSeedling → DbSeedlingChangeWriter`.
Порт читает свежую партию; все новые всходы сохраняются одним SaveChanges.
`SeedlingBatchDbMapper` — общий маппинг состояния и DTO результата; UI применяет
результат через ApplySeedlingChange только после успеха. Количество 0 означает
неограниченный посев по весу; при положительном количестве используется целая
часть. Нулевой ввод всходов сохраняет прежнюю отметку единственной записи погибшей.
Номер нового всхода продолжает счёт всех записей с датой, включая погибшие.

Пересадка и гибель используют тот же ChangeSeedling через Replant/MarkDead.
Редактор рассады хранит SeedlingEditorDraft с независимыми строками, не EF-граф.
EditSeedling проверяет SeedlingDetails/SeedlingEdit, пересчитывает фазу календарём
и сохраняет только редактируемые поля через DbSeedlingEditWriter. Метаданные первой
записи и дублирующие поля партии синхронизируются общим SeedlingDetailsDbMapper;
SeedId, растение, PlantedOut, IsPlantedInBed, карантин, обработки и история не
переписываются. Новые записи, появившиеся после открытия черновика, сохраняются.
Отмена пересоздаёт черновик из кэша; отказ сохраняет ввод. Ошибки WPF-привязок
блокируют сохранение. Старый SeedlingMapper.CopyInto больше не обслуживает UI.

SeedlingBatch вычисляет GerminatedCount, AliveCount и AvailableCount = AliveCount −
PlantedOut. Все With-переходы и редактирование сохраняют высаженное количество.
DTO результата возвращает свежее PlantedOut для кэша. Исторический отрицательный
остаток не обнуляйте молча: он остаётся видимым дефицитом, как в прежней модели чтения.

Высадка рассады в ячейку использует чистый `SeedlingBatch.PlantOut`: расход ограничен
живыми доступными всходами, затем округляется Math.Round (ToEven), как в прежнем
сервисе. Нулевой, отрицательный, неконечный и округлённый в ноль расход дают отказ.
Результат содержит новый снимок и фактическое число штук; исходный снимок не меняется.
`PlantingService` преобразует WPF-запрос в закрытые варианты PlantingSource с
проверенными SeedId/SeedlingId и делегирует Application/Garden/PlantInSpot.
SpotPlanting проверяет ячейку, дату и расход; фаза вычисляется через ILunarCalendar.
DbPlantingWriter читает свежие данные и сохраняет счётчик/остаток, новую партию и
ячейку одним SaveChanges. Прямой посев использует SeedStock.SowUpTo: ограничение
остатком, округление только штук, затем существующий Sow. Неизвестный вес и
округление сверх дробного остатка дают явный отказ, расход не подменяется нулём.
SeedPackageDbMapper.ReadStock общий для посева в рассаду и в ячейку.
Result возвращает ID записи, фактический расход и свежий остаток с единицами;
UI устанавливает этот остаток после успеха, при отказе сохраняет ввод и показывает
причину. PlantSources находится в Domain/Seeds; значения строк БД не менять.
Переходы состояний, TPH и Composite пока прежние; детали — plans/refactoring-stage-6.md.

Перестройка сетки UI проходит через `GardenService.ResizeGridAsync → ResizeGrid →
DbGridWriter`. GridSize проверяет неотрицательные размеры и диапазон числа ячеек;
нулевой размер сохраняет прежнюю очистку. Чистый GardenGrid.WithSize рассчитывает
только удаляемые/добавляемые позиции и проверяет CanModifyGrid. DbGridMapper общий
для нового сценария и прежнего RebuildGridAsync; существующие ячейки не заменяются,
их ID/состояния/заметки/даты/ссылки сохраняются. Порт читает свежий элемент, пишет
размеры и ячейки одним SaveChanges, возвращает DTO внутри Result. UI обновляет
сетку только после успеха, при отказе сохраняет ввод и выбранную ячейку.
IsLocked остаётся блокировкой геометрии, не сетки. Удаление ячеек за границами
сохраняет самостоятельные SeedlingInfo/историю пересадок; данные самой удалённой
ячейки удаляются по прежним правилам. Старый EF-API перестройки больше не вызывается
из UI и остаётся совместимостью до этапа 7.

Переходы элемента, теплицы, ячейки и очистка проходят через ChangeGardenState и
DbGardenStateWriter. GardenStateChange проверяет ID/закрытую цель, порт читает свежий
объект и меняет только нужные поля одним SaveChanges. PlantingCell — иммутабельный
снимок ячейки; Apply использует существующий TransitionTo. None метки сохраняет
Note, Some сохраняется точно. Clear сбрасывает состояние, связь и даты, сохраняя
Note и самостоятельную историю рассады. DTO ячейки общий с результатом сетки.
UI применяет результат только после успеха; очистка скрывает подпись и сбрасывает
ссылку в кэше, сохраняя Note. Старые EF-API переходов остаются совместимостью без
вызовов из UI. Уборка меняет статус, не назначая автоматически дату уборки.

Пересечения и поиск места находятся в Domain/Garden/CanvasGeometry.cs:
CanvasRectangle проверяет конечность координат/размеров/краёв и неотрицательные
размеры; PlotLayout хранит immutable-снимок препятствий и возвращает
Result<Option<CanvasRectangle>>. None — места нет, Failure — неверная геометрия.
CollisionHelper — адаптер моделей UI; исключайте себя по ссылке до проекции в
значения. FindPlacement возвращает Result/Option; добавление показывает ошибку до
записи. FindFreeSpot с nullable оставлен совместимостью для этапа 7. Прежний
численный bool-предикат общий в CanvasIntersection, включая поведение NaN и
нулевых размеров; не добавляйте в старые drag-проверки исключения валидации.
Rotation пока не учитывается; запись геометрии ещё использует прежние EF-API.

Расчёты жестов находятся в CanvasRectangle.WithMoved/WithResized/ResolveDropFrom.
CanvasBounds хранит известные границы через Option; адаптер сохраняет прежний
критерий UI «размер > 0», не путайте его с общим nullable ↔ Option. Перемещение
ограничивается до округления к 15 DIPs (ToEven); resize округляется до целых с
минимумом 15 для элемента и 150 для теплицы, даже если контейнер меньше.
CanvasScale — единственный WPF-поиск масштаба с прежним fallback 1. CanvasGestureAdapter
и общий CanvasGeometryMapper связывают модели с доменом. Code-behind хранит Option
снимка начала жеста, фокус и применение результата; порядок XAML-сохранения прежний.
Откат нужен только при новой коллизии: исходные пересечения разрешены. Без отката
не повторяйте записи свойств/INPC. Некорректный расчёт не применяется и попадает
в Trace; ошибки записи геометрии показываются через IUserDialog.

Жесты сохраняют геометрию через `SaveGardenGeometry → GardenGeometryEdit →
DbGardenGeometryWriter`. Закрытые варианты Element/Greenhouse не смешивают внешние
размеры теплицы с её внутренним холстом. Площадь элемента вычисляет Domain из
размеров и переданного WPF-масштаба; масштаб и результат проверяются на конечность.
Порт читает свежий объект и соседей только его контейнера, проверяет IsLocked и
новые пересечения, записывает только X/Y/DisplayWidth/DisplayHeight и площадь
элемента одним SaveChanges. Исходные пересечения разрешены; строгую проверку края
после округления не добавляйте. Сам объект исключается по типу и ID, совпадение
численных ID разных таблиц не исключает соседа. Состояние, Rotation, метаданные,
сетка и Composite не меняются. PlotLayout.Create общий для чтения препятствий.
XAML передаёт объект жеста явно; результат применяется к захваченному объекту,
даже если выбор изменился во время await, без повторных INPC для прежних значений.
Отказ сохраняет предварительную геометрию и показывает причину. Кнопки свойств
отделены от жестов. Внутренние размеры теплицы, блокировки и оставшиеся CRUD
пока используют прежние EF-API; весь этап ещё не завершён.

Редактор элемента использует независимый ElementEditorDraft в обоих холстах:
ElementEditorMapper → EditElementProperties → ElementPropertiesEdit →
DbElementPropertiesWriter. Исходный снимок и ввод — иммутабельные ElementEditorValues;
WithChangesFrom общий для слияния со свежей записью и принятия результата в UI.
Применяйте только изменённые относительно снимка поля; нетронутые значения берите
из свежей записи. Имя, включая пустую строку и пробелы, не нормализуется; Note и
SoilType сохраняют различие None/Some(""). Orientation принадлежит Bed,
CoverMaterial — ColdFrame; Shape, Rotation, состояние, сетка и история не меняются.
Изменение геометрии проверяется через GardenGeometryEdit; площадь пересчитывается
только при таком изменении. Метаданные разрешены при IsLocked, геометрия — нет.
DbCanvasSiblings общий для редактора и жестов; вся запись выполняется одним SaveChanges.
Кэш меняйте только после успеха; отказ сохраняет черновик, отмена перечитывает кэш.
После await применяйте результат к исходному объекту и принимайте его в редакторе
только если выбран тот же объект; последующий ввод сохраняется через WithChangesFrom.
Успешный жест обновляет нетронутые поля черновика, сохраняя его изменения; при ошибке
привязки черновик не пересоздаётся. CheckedPxToMeters включает строгий режим
существующего конвертера: неверное/неконечное число не подменяется нулём, блокирует
сохранение; отмена сбрасывает ошибку. Остальные потребители конвертера совместимы.
Редактор самой теплицы остаётся следующей частью 4в2б.

## Сборка, запуск и тесты

Работайте в Windows с SDK из `global.json`. Команды выполняйте из корня:

- `dotnet restore Bonfire.sln` — восстановить зависимости.
- `dotnet build Bonfire.sln` — собрать решение.
- `dotnet run --project Bonfire/Bonfire.csproj` — запустить приложение.
- `dotnet test Bonfire.sln` — выполнить все тесты.
- `dotnet test Tests/Services.Tests/Services.Tests.csproj` — проверить сервисы.
- `dotnet run --project Tests/Startup.Smoke/Startup.Smoke.csproj` — проверить настоящий WPF startup/exit с невидимым окном и новой SQLite в каталоге smoke-проекта; рабочая БД не используется.
- `git config core.hooksPath .githooks` — подключить pre-commit; предварительно собирайте решение, поскольку хук использует `--no-build`.

Используйте xUnit, NSubstitute и существующие EF InMemory/SQLite fixtures. Имена: `*Tests.cs`, `Method_Scenario_ExpectedBehavior`. Добавляйте регрессионные проверки поведения и сохранения данных. Coverlet доступен; числового порога покрытия нет.

## Процесс разработки и доказательства

- Перед существенным изменением уточните цель и критерии готовности, проследите путь от UI через модель и сервис до БД. Найдите существующие свойства, словари, мапперы и контракты; переиспользуйте их вместо создания смысловых дублей.
- Составляйте план по этапам: цель, затрагиваемые файлы, последовательность действий, при необходимости псевдокод, тест-гейт и критерии готовности. Отмечайте подтверждённые результаты и открытые вопросы отдельно.
- До изменения контракта или маппинга подтвердите смысл исходного и целевого поля по коду, тестам, схеме и доступным данным. Не угадывайте назначение по одному имени или комментарию. Неоднозначности и непокрытые данные обсуждайте с владельцем; не пропускайте и не подменяйте их молча.
- Перед рефакторингом проверьте вызывающий код, зависимости и затронутые тесты. Если в текущем проекте доступен CodeGraph, перед графовыми запросами обновляйте индекс (`sync`), затем используйте `query`, `callers`/`callees`, `impact`, `affected`. Иначе используйте `rg` и чтение кода; не считайте индекс другого репозитория доказательством для Bonfire.
- Этап завершается проверкой поведения. Падающие проверки исправляйте до следующего этапа; инфраструктурный блокер фиксируйте явно. План и предположение не являются доказательством реализации.

## Порядок разработки: TDD (обязательно)

Перенесённые правила дополняют TDD и не отменяют его.

Для нового поведения и исправления ошибок соблюдайте цикл Red → Green → Refactor:

1. **Red:** сначала добавьте тест ожидаемого поведения в соответствующий проект `Tests/`. Запустите его и убедитесь, что он падает по ожидаемой причине, а не из-за ошибки окружения.
2. **Green:** внесите минимальные изменения реализации, необходимые для прохождения теста, и повторно запустите затронутые тесты.
3. **Refactor:** при необходимости улучшите изменённый код без расширения задачи; после изменений тесты должны оставаться зелёными.
4. Перед завершением выполните `dotnet test Bonfire.sln` и укажите результаты проверки. Если запуск заблокирован, сообщите причину; не объявляйте тесты пройденными.

Проверяйте наблюдаемое поведение, а не детали реализации. Для изменений только документации или визуальной XAML-разметки без изменения поведения тесты не требуются; разметку проверяйте сборкой и визуально.

Тест-гейт Bonfire — все пять проектов `Tests/`, а не набор проектов исходного AIXM-приложения. Отдельную проверку запускайте через `dotnet test <project> --filter "FullyQualifiedName~ClassName.MethodName"`. В тестах не хардкодьте диски и разделители путей: используйте `Path.Combine`; для фиктивного абсолютного пути — `Path.Combine(Path.GetTempPath(), ...)`.

## Техническая документация

- Ведите документацию параллельно разработке, но содержательное описание нового или существенно изменённого слоя пишите после стабилизации модели, маппинга и DB-контракта, когда остаются финальные проверки. Ранний черновик отмечайте как черновик.
- Завершайте документацию в том же PR либо следующим PR до признания задачи выполненной. После принятия изменение публичного поведения, маппинга, зависимостей или диагностик сопровождайте обновлением документации в том же PR.
- Сверяйте утверждения с текущим кодом, unit/integration-тестами и артефактами проверок. Описывайте назначение, поток данных, зависимости, правила валидации и ошибок, конфигурацию и ограничения. На большие доказательные таблицы и результаты аудита давайте ссылки вместо копирования.

## Стиль и доменные соглашения

Используйте четыре пробела, file-scoped namespaces, отдельные строки для скобок, PascalCase для типов/методов, `_camelCase` для полей и суффикс `Async`. Сохраняйте nullable; в `Bonfire` пишите явные `using`. Комментарии и UI — по-русски. Общего formatter-конфига нет.

Окна и диалоги оформляйте в XAML, данные и привязки — через ViewModel. Не собирайте визуальное дерево окна вручную в сервисах; code-behind оставляйте для действий представления, например установки DialogResult.

Для новой доменной логики предпочитайте богатые иммутабельные модели, value-объекты, strongly-typed ID и чистые функции. Изменения иммутабельных агрегатов выражайте через `With…`, возвращающий новый экземпляр; используйте `init`, records, collection expressions и pattern matching там, где они подходят. Существующие EF-сущности и WPF-модели не переводите на другой контракт попутным рефакторингом.

Ожидаемые ошибки представляйте через существующие `Result`/`Option`/`Error`, если соответствующий тип уже есть; не создавайте параллельный toolkit и не заменяйте результат сочетанием `bool` и nullable. Исключения проверки инвариантов, например `ArgumentNullException` в конструкторе, сохраняйте. Для закрытых наборов с поведением используйте полиморфные sealed-варианты; enum допустим для инертного дискриминатора.

Для справочных значений и преобразований код → значение ищите и расширяйте существующий общий механизм разрешения. Не размножайте локальные словари, `switch` и захардкоженные DB ID; новый вариант добавляйте в одном месте с проверкой его семантики.

DTO называйте `*FromViewModel`; маппинг выполняйте вручную, без AutoMapper. Сущности добавляйте в `Entities/` и регистрируйте в `DbBonfire`. Не возвращайте ограничение `new()` для абстрактных сущностей.

Состояния реализуйте полиморфно, без enum; существующие иерархии находятся в
`Bonfire.Domain/Garden/States/` и `SpotStates/`. Расширяйте их и фабрики `From()`;
не создавайте копии правил в EF или UI. Чистый `TransitionTo` возвращает Result,
не меняя исходное состояние; EF-сущности делегируют ему, сохраняя прежние исключения
на границе совместимости. `CanTransitionTo` остаётся проверкой доступности UI.
Сохраняйте строковый `StateTypeName`, TPH-дискриминаторы, оформление и Composite
теплицы. Фабрики From пока сохраняют прежний fallback неизвестных строк;
не считайте это строгой проверкой нового входного контракта.

Для закрытых иерархий с sealed-вариантами реализуйте `Map` extension-методом отдельного статического класса с исчерпывающим pattern matching. Не добавляйте абстрактный `Map` и однотипные override без собственной логики. Метод экземпляра допустим для поведения доменного типа.

## База данных

Настройки SQLite находятся в `Bonfire/appsettings.json`; `DbInitializer` применяет миграции при запуске. Создавайте миграции командой `dotnet ef migrations add <Name> --project BonfireDB --startup-project Bonfire`.

`DbInitializer` разрешайте только внутри DI-области. `Program.CreateHostBuilder` — общий composition root со строгой проверкой DI; окно открывается после асинхронной инициализации и запуска host. Закрытие окна ожидает остановку и освобождение host до завершения Dispatcher.

## Коммиты и pull requests

Новая задача — feature-ветка (`git switch -c feature/<name>`); прямые коммиты в `master` запрещены, merge — только по явному запросу. При делегировании используйте изолированные worktree.

Пишите сфокусированные коммиты `feat:`, `fix:` или `fix(ui):` с описанием по-русски. В PR указывайте изменения поведения, связанные задачи, результаты тестов и скриншоты WPF.

Копирование и синхронизацию изменений в другой рабочий репозиторий выполняйте только по явному разрешению владельца; до записи подготовьте проверяемый diff или dry-run. Скрипты и пути синхронизации AIXM-проекта к Bonfire не относятся.
